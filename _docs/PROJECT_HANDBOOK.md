## 0. Что это за продукт

**Dentovox** — ИИ-ресепшионист для стоматологических клиник США. Отвечает на входящие звонки пациентов: записывает на приём, переносит, отменяет, ставит в лист ожидания, сортирует неотложные случаи. Плюс исходящий обзвон «спящих» пациентов (реактивация).

Клиника платит подписку. Тарифы: $249 / $399 / $599 / $899 в месяц.

**Стадия:** предзапуск. Одна пилотная клиника, реальных платящих клиник нет. В базе 7 практик — тестовые. Телефонных звонков через продовый агент почти не было; основной трафик пока web-звонки из дашборда.

**Кто в проекте:** владелец (нетехнический, принимает все решения, вводит все ключи) + ИИ-агенты. Постоянного инженера нет. Это определяет многие архитектурные решения: операционная нагрузка — реальная стоимость, а не сноска.

## 2. Как устроен звонок, от гудка до записи в базе

Это главная схема проекта. Всё остальное — обвязка.

```
Пациент звонит
   │
   ▼
Retell AI  ── телефония (Twilio под капотом), STT, LLM, TTS, barge-in
   │
   │ 1. ДО ответа: POST /webhooks/retell/inbound
   │    → мы отвечаем словарём динамических переменных этой клиники
   │      (имя, адрес, часы, база знаний, сегодняшняя дата, открыт ли офис)
   │
   │ 2. call_started → POST /webhooks/retell → создаём строку в calls
   │
   │ 3. Агент вызывает тулы → POST /webhooks/retell (function_call)
   │    check_availability / book_appointment / reschedule / cancel /
   │    join_waitlist / lookup_patient / create_callback_request /
   │    transfer_to_human
   │
   │ 4. call_ended → длительность, расшифровка, классификация исхода
   │ 5. call_analyzed → уточнение исхода по анализу Retell
   ▼
Наш бэкенд ── Postgres (RLS на клинику) + Twilio SMS + PMS клиники
```

**Ключевой факт, который объясняет половину багов проекта:** Retell подставляет в промпт **только те переменные, которые мы прислали**. Плейсхолдер, который промпт использует, а мы не заполнили, произносится пациенту буквально: «Today is {{today}}». Это уже случалось дважды. Есть тест, который падает со списком таких плейсхолдеров.

**Второй ключевой факт:** настройки голоса живут на объекте **агента** в Retell, а промпт и тулы — на объекте **LLM**. Правка одного не трогает другое. Каждый `publish-agent` создаёт новую версию агента и публикует предыдущую — смотреть надо `get-agent-versions/$AGENT_ID` и поле `is_published`.

## 3. Бэкенд

### 3.1 Стек и почему он

- **FastAPI** + **async SQLAlchemy 2** + **Alembic** + **Postgres**. Асинхронность здесь не мода: тул-вызов происходит посреди живого разговора, каждые лишние 200 мс слышны.
- **Pydantic v2 / pydantic-settings** — все переменные окружения в одном `app/config.py` (78 настроек), с нормализацией URL БД под asyncpg.
- **slowapi** — rate limiting.
- **Sentry** — ошибки.
- Зависимости намеренно скучные. Ни очередей, ни Celery, ни Redis: фоновые задачи — обычные asyncio-циклы с блокировкой через Postgres advisory lock.

### 3.2 Структура

```
app/
  routes/       19 модулей — HTTP API кабинета и админки
  models/       23 модели SQLAlchemy
  webhooks/     retell.py (~2000 строк, главный), stripe.py, clerk.py, twilio_sms.py
  services/     availability, sms, reminders, call_sync, call_outcome, worker_lock,
                billing_service, pricing, telephony/, reactivation/, qa/, llm/,
                assistant/, legal/
  adapters/     nexhealth/ (боевой), open_dental/ (модели + мок)
  auth/         permissions.py (роли и права), admin.py (внутренний персонал)
  billing/      metering.py, plans.py
  observability/ alerts.py
migrations/versions/   40 миграций, голова: n5c6d7e8f9a0
tests/                 678 тестов, все зелёные
```

### 3.3 Мультиарендность — самое важное место

Одна база Postgres на все клиники. Изоляция — **Row-Level Security с FORCE**, политики читают `current_setting('app.current_practice_id')`.

Политики **fail-closed**: если переменная не установлена, запрос вернёт **ноль строк**, а не все. То есть забытый tenant-фильтр даёт пустоту, а не утечку.

```
Запрос кабинета → зависимость резолвит клинику по Clerk-организации
               → set_tenant(session, practice_id)  ← ставит GUC на соединение
               → RLS пропускает только строки этой клиники
```

Таблицы под обязательным RLS (проверяется CI-гейтом `scripts/check_rls_coverage.py`): `patients`, `calls`, `bookings`, `callback_requests`, `waitlist_entries`, `invitations`, `reactivation_campaigns`, `reactivation_targets`, `reactivation_touches`.

**Дыра, которую закрыли 1 августа:** прод подключался к БД суперпользователем, а суперпользователь **освобождён от всех политик RLS**. То есть вся изоляция была украшением — молча, без ошибок. Сейчас `GET /health/detailed` отдаёт `"rls_enforced": true`, это надо проверять при каждом ревью.

Чтобы это стало возможным, понадобилось **второе соединение**: внутренняя админка и кросс-клиничный QA читают все клиники сразу, под RLS они получали бы пусто. `DATABASE_URL_PLATFORM` — единственный путь к таким чтениям, `platform_session_factory` в `app/db.py`. Каждое использование грепается за секунду, и есть тест, что ни один роут админки не съехал обратно на арендный фактори.

### 3.4 PHI и шифрование

Шифруются Fernet'ом на уровне типа колонки (`EncryptedString` / `EncryptedJSON` в `app/models/types.py`):
- `patients`: имя, фамилия, телефон, email, дата рождения
- `calls`: номера сторон, расшифровка разговора, путь к записи
- `callback_requests`: имя, телефон

Поиск по зашифрованному телефону — через детерминированный `phone_hmac` (HMAC-SHA256 от нормализованного номера), индексируется. Ротация `ENCRYPTION_KEY` требует пересчёта хэшей: `scripts/backfill_phone_hmac.py`.

В логи PHI не пишется: только id и последние 4 цифры телефона.

### 3.5 Фоновые воркеры

Четыре asyncio-цикла стартуют вместе с приложением (`app/main.py`), каждый под **advisory-локом Postgres** — при нескольких инстансах Railway тик выполняет только один:

| Цикл | Что делает |
|---|---|
| `call_sync_loop` | Дотягивает из Retell звонки, чьи вебхуки потерялись |
| `reminder_loop` | Напоминания пациентам за ~24ч и ~2ч. Захват через `FOR UPDATE SKIP LOCKED`, отметка **до** отправки: при падении лучше потерять напоминание, чем отправить дважды |
| `maintenance_loop` | Уборка |
| `reactivation_worker_loop` | Исходящий обзвон и SMS спящим пациентам |

Ключ advisory-лока считается через `blake2b`, а не через `hash()` — питоновский `hash()` солится по процессам и тихо ломает выборы лидера.

### 3.6 Деньги

`app/billing/` — метеринг минут (upsert по `(practice_id, period_start)`), Stripe-подписки, инвойсы. Вебхуки Stripe идемпотентны через таблицу `processed_webhook_event`.

`ESTIMATED_COST_CENTS_PER_MIN = 17` — стоял `8`, то есть маржа в админке показывалась примерно вдвое завышенной. Исправлено 1 августа.

## 4. Голосовой слой

### 4.1 Что делает Retell, а что мы

**Retell делает всё, кроме бизнес-логики:** дозвон, распознавание речи, запуск LLM, синтез речи, обработка перебиваний, определение конца реплики. Мы отвечаем только на вебхуки тулов.

Это полная зависимость от вендора: их простой = наш продукт не работает. Решение осознанное — построить свой голосовой стек до PMF значило бы месяцы инженерной работы без продуктового обучения. Пересматривать после ~10 клиник (см. §9).

| LLM ID | `llm_ceb34907c41312c609929a14340d` |

### 4.3 Промпт и тулы

`dentiva-voice/agents/front_desk_v1/`:
- `system_prompt.md` — 16 766 символов. Законы разговора, поток записи, два тира неотложности, правила эскалации, идентификация пациента, исходящий сценарий.
- `functions.yaml` — 11 тулов.
- `voice_settings.yaml` — голос, чувствительность, словарь произношения.
- `config.yaml` — модель, температура, вебхук.

Синк в Retell: `python3 scripts/sync_agent.py` (есть `--dry-run`). Скрипт отправляет **весь** список тулов — то, чего нет в `functions.yaml`, удаляется с живого агента. Есть тесты (`dentiva-voice/tests/test_sync_payloads.py`), которые проверяют payload перед отправкой: плейсхолдеры не разрешены, пример-имя клиники не уезжает, нативные тулы на месте, голос совпадает с продовым.

### 4.4 Безопасность, не зависящая от модели

Модель можно уговорить. Поэтому критичное сделано программно, в роутере тулов (`app/webhooks/retell.py`):

**Блокировка расписания при неотложности.** Детерминированный регексп сканирует аргументы **любого** тула. При срабатывании `check_availability`, `book_appointment`, `reschedule_appointment` физически отказывают, а флаг `calls.emergency_active` сохраняется в БД — переживает перезапуск и действует весь звонок.

**Два тира:**
- Тир 1 — угроза жизни (затруднённое дыхание/глотание, отёк лица/горла/языка, неостанавливающееся кровотечение, потеря сознания) → пациента направляют в 911/приёмный покой **в любой час**, запись и колбэк не предлагаются.
- Тир 2 — срочная стоматология (сильная боль, выбитый зуб) → срочный колбэк с формулировкой, знающей часы работы клиники.

**Что сканер намеренно не читает:** значения из фиксированных списков (`procedure`, окна времени, даты, телефоны). Раньше читал — и тип визита `emergency`, который мы продаём, блокировал сам себя, залипая на весь звонок.

**Отрицания:** «no swelling, no fever» больше не запирает звонок. Но отрицание не переносится через «но»: «температуры нет, **но** лицо отекает» срабатывает. Недосработать здесь опаснее, чем перестраховаться.

**Проверка личности.** `lookup_patient`, `reschedule_appointment`, `cancel_appointment` требуют одного из трёх: звонок с номера, привязанного к записи; совпадение даты рождения; либо этот же звонящий уже забронировал как этот пациент в этом же звонке. Отказ не выдаёт ни имени, ни факта существования записи.

**Эскалация.** Три канала: нативный холодный перевод (срочная стоматология, офис открыт, номер задан), нативный тёплый перевод (всё остальное), срочный колбэк (нет номера / закрыто / перевод сорвался). Кастомный тул **никогда** не может соединить звонок — это умеет только нативный `transfer_call`. Раньше кастомный тул отвечал «соединяю», и пациент слушал тишину.

**Падение бэкенда посреди звонка** не даёт 500: диспетчер тулов возвращает агенту произносимый текст с запретом утверждать, что что-то записалось.

### 4.5 QA-петля

`app/services/qa/call_review.py`:
- LLM-разбор звонков с неудачным исходом → повторяющиеся паттерны → предложения правок промпта. Никогда не правит промпт сам.
- Детерминированный сканер **всех** расшифровок на обещания, которые продукт не выполняет («соединю вас»). Именно потому, что ложное обещание завершается как обычный звонок и разбор по исходам его не увидит.
- Разбор идёт **только через Anthropic**, без падения на вендора без BAA: расшифровки — это PHI. Если ключа нет, разбор пропускается, а не уходит к другому вендору.

## 5. Фронтенд

Next.js 14.2 (App Router), React 18, TypeScript, Tailwind, Clerk, TanStack Query, Zod. 32 страницы, 48 компонентов, 19 хуков, 18 схем.

**Две аудитории в одном приложении:**
- `app/(dashboard)/` — кабинет клиники: обзор, звонки, брони, пациенты, колбэки, лист ожидания, реактивация, аналитика, база знаний, настройки, команда, биллинг.
- `app/admin/` — внутренняя админка: клиники, выручка, тарифы, купоны, лиды, персонал, фича-флаги, здоровье системы, QA звонков, аудит-лог.

Перекрёстных импортов между ними нет (проверено грепом). Правило держится на дисциплине, не на линтере.

**Данные:** все страницы клиентские, ходят в FastAPI через `lib/api/client.ts`. Это единственная точка, где ответ валидируется Zod-схемой — бизнес-код невалидированных данных не видит.

**Известный класс багов:** схема на фронте строже, чем бэкенд → валидный ответ падает, страница показывает «не удалось загрузить». Уже случалось со статусом звонка и с `duration_seconds`. При ревью смотреть на `z.enum` и на nullable.

**Пустое ≠ сломанное.** После включения RLS запрос без клиники возвращает пусто. Поэтому `EmptyState` различает три состояния: фильтр ничего не нашёл (с кнопкой сброса), клиника на онбординге, живая клиника без данных (отдельная строка «скажите нам, это ненормально»).

## 7. Как проверить, что всё живо

```bash
# Прод здоров, изоляция включена
curl -s https://dentiva-backend-production.up.railway.app/health/detailed
# ждём: "status":"ok", "db":"ok", "rls_enforced":true, alerts.count_last_hour:0

# Тесты бэкенда (~4 минуты, нужен локальный Postgres)
cd dentiva-backend && source .venv/bin/activate && python -m pytest -q
ruff check app tests

# Фронт
cd dentiva-dashboard && npx tsc --noEmit && npm run lint && npx vitest run && npm run build

# Что реально настроено у живого агента (репозиторий может врать — проверяли)
cd dentiva-voice && python3 scripts/sync_agent.py --dry-run   # payload без отправки
curl -H "Authorization: Bearer $KEY" https://api.retellai.com/get-agent/$AGENT_ID
```

В админке есть карточка **Live agent** (Admin → System health): читает живого агента и называет расхождения человеческим языком — обещает ли промпт соединение, есть ли ветка скорой, есть ли нативный перевод, знает ли колбэк часы работы.

**Правило, выведенное кровью:** конфиг агента проверять через API, а не по файлам репозитория. Репозиторий и прод расходились дважды.

## 8. Что сделано, что сломано, что не начато

### Работает и проверено на живом звонке
Цикл звонок → бронь → дашборд. Честная эскалация. Ветка скорой. Часы работы в обещаниях. SMS клинике на бронь и на срочный колбэк. Проверка личности. QA-петля со сканером ложных обещаний. Дрейф-детектор агента. Покупка номера на клинику с коммерческим гейтом.

### Сделано, но вживую не проверено
- **Нативный перевод звонка.** Мост через телефонную сеть на web-звонке не задействуется. Нужен телефонный тест с заполненным transfer-номером клиники.
- **Мост с PMS.** Слоты из календаря клиники и запись обратно — код есть, тесты есть, но включается только при заполненных `NEXHEALTH_*` и реальном `pms_system` у клиники. Пока переменных нет, работает старое поведение.

### Честные ограничения, не баги
- **Пациент, встреченный по телефону, не попадает в PMS.** У него id вида `VOICE-…`, в системе клиники его нет. Приём против неизвестного пациента создать нельзя → алерт `pms_patient_not_in_pms`, ресепшен добавляет вручную. Создание пациента в PMS не реализовано: у клиента нет проверенного эндпоинта, а отправлять непроверенный вызов в чужой API нельзя.
### Какой мост к PMS брать — считано, не угадано

Клиника работает на Eaglesoft, Dentrix или Open Dental, и почти ни одна из них
не разговаривает с нами напрямую: Patterson просит $3–5K за вход в свою
программу, Dentrix — $5 000. Поэтому идём через агрегатор, и выбор между двумя
меняется с ростом числа клиник.

| | цена | оговорка |
|---|---|---|
| **Open Dental напрямую** | $30/локация | только для клиник на Open Dental, минимума нет |
| **NexHealth** | $75/локация | минимума нет |
| **Kolla Unify, только чтение** | $19/локация | **минимум 10 локаций** |
| **Kolla Unify, с записью** | $29/локация | **минимум 10 локаций** |

Заявленные Kolla «$19» нам не подходят: это тариф только на чтение, а агент,
который не может записать пациента, бессмыслен. Нужен тариф с записью — $29 — и
минимум в десять локаций означает **счёт от $290/мес независимо от того, сколько
у нас клиник**.

Отсюда точка перехода:

| клиник | NexHealth | Kolla (макс из $290 и $29×N) |
|---|---|---|
| 1 | **$75** | $290 |
| 3 | **$225** | $290 |
| **4** | $300 | **$290** ← перелом |
| 10 | $750 | **$290** |
| 20 | $1 500 | **$580** |

**До четырёх клиник — NexHealth. С четырёх — Kolla.** Это переключение
настройкой: `app/adapters/bridge.py` выбирает мост по заданным ключам, оба
адаптера написаны и покрыты тестами.

Цифра важна тем, что она обратная интуиции: Kolla рекламирует себя как дешёвую и
на объёме действительно дешевле вчетверо, но на первой клинике дороже вчетверо.
Минимум в десять локаций — одна строка мелким шрифтом на странице, которая не
читается без браузера.

### Что песочница NexHealth умеет, а что нет

Проверено на живом API 11 августа: каталог работает — 5 пациентов, 5 врачей,
3 кабинета, 10 типов приёмов. **Оба эндпоинта расписания — `appointment_slots` и
`availabilities` — отвечают «Resource not found».**

Это не поломка. NexHealth считает свободные окна из синхронизированной PMS, а к
песочнице ничего не подключено. Их поддержка подтверждает: чтобы проверять
расписание, к песочнице надо привязать демо-среду Open Dental — а она ставится
только на Windows.

Ещё одна вещь, стоившая нам круга проверок: `21882` — это идентификатор
**института**, а локация — `351939`. Эндпоинт `/locations` возвращает первый, что
и сбило нас; правильное значение подтвердила их поддержка.

- **Доступы к PMS глобальные**, из переменных окружения. Для одной клиники нормально, для второй — нет. Поле `pms_credentials_secret_key` в модели есть, но ничем не читается.
- **Испанский в регексп-защите не покрыт.** Промпт обещает испанский, а `_EMERGENCY_PATTERNS` — только английский. Пациент, описывающий удушье по-испански, не активирует программную блокировку. Модель его поймёт, а вот защита, не зависящая от модели, — нет.
- **Блокировка неотложности срабатывает только на аргументах тулов.** Если модель вообще не распознала неотложность и вызвала запись с чистыми аргументами — бэкенд ничего не увидит. Защита от «распознал, но всё равно пытается записать», а не от «не распознал».

### Блокеры до первой платящей клиники
1. **BAA с Retell** — подписан ли, какой тариф, покрывает ли ElevenLabs как субподрядчика. **Не проверено.** Это блокер сам по себе.
2. **Тарифная сетка.** Овередж на трёх тарифах из четырёх дешевле себестоимости минуты (15¢/13¢/11¢ против 17.3¢), и ставка падает с ростом тарифа. Клиника растёт — мы теряем больше.
3. Stripe в боевом режиме, Clerk production.
4. Разделение Retell-аккаунтов Dentovox и B&H.
5. Ротация пароля роли `dentiva_app` (текущий засветился в переписке).

### Технический долг, названный ревьюерами
- `app/webhooks/retell.py` — ~2000 строк, один модуль на все тулы, жизненный цикл звонка и резолв клиники. Швы для разделения названы: HTTP-слой, резолв клиники, по модулю на тул, жизненный цикл.
- `app/services/booking.py` — мёртвый код от ранней фазы.
- Контракт бэкенд↔фронт синхронизируется вручную через `_shared/API_CONTRACT.md`. Уже ломался.

## 9. Экономика

**Замер на реальном звонке 31 июля** (99.4 с, разбивка от Retell):

| Компонент | ¢/мин |
|---|---|
| Движок Retell (включая STT, отдельно не выбирается) | 5.5 |
| ElevenLabs Flash TTS | 4.0 |
| gpt-4.1 | 4.5 |
| Надбавка за токены промпта | 0.9 |
| **Итого web-звонок** | **15.8** |
| Телефония (на телефонном звонке) | +1.5 |
| **Итого телефонный звонок** | **17.3** |

Плюс ~1.5¢ за звонок на пост-анализ и $2/мес за номер.

**Где реально можно сэкономить без потери качества:**
1. TTS: ElevenLabs 4.0¢ → любой из бандла Retell 1.5¢ (Cartesia, Minimax, Fish, OpenAI, native) = **−2.5¢/мин**. Переключается селектором. Требует проверки: 20 звонков, из них 10 испанских, плюс скрипт из телефонных номеров и дат.
2. Промпт короче → надбавка за токены пропорционально меньше, ещё **−0.4…0.5¢/мин** (оценка).

Итого **−17%** без единого риска для модели.

**Смена модели — только через гейт на цифрах.** Дешёвый тир уже коверкал телефонные номера на реальном звонке. Порядок кандидатов: `gpt-5.4-mini` (3.6¢), `claude-4.5-haiku` (2.5¢), `gpt-4.1-mini` (1.6¢). Nano-тиры (0.3–1.0¢) для телефонного пути не рассматривать.

**Уход с Retell считали honestly:** LiveKit + Deepgram + Cartesia + Twilio ≈ 8–10¢/мин против 17.3¢. Но BAA у LiveKit — с тарифа $500/мес, что на 2000 минутах даёт +25¢/мин и съедает экономию целиком. Плюс инженерные месяцы на barge-in и определение конца реплики — ровно то, что Retell и продаёт. Open source ещё хуже: GPU простаивает 95% времени, эффективно 18–40¢/мин. **Вывод: не раньше ~10 клиник и не раньше появления инженера с опытом продакшн-голоса.**

## 10. Процесс работы

Код → тесты → `ruff` → ветка → PR → CI → merge → автодеплой → проверка прода.

CI бэкенда (`backend-ci.yml`) поднимает Postgres, создаёт роли, гоняет ruff, 678 тестов и **гейт покрытия RLS** на отдельной БД с настоящими миграциями.

`claude-review.yml` во всех трёх репозиториях — ревью Антропика на каждый PR. Пропускается, пока не задан секрет `ANTHROPIC_API_KEY`, чтобы не висел красный чек.

**Правила, которые стоит соблюдать новому агенту:**
- Не запускать pytest параллельно с другим агентом: тесты используют одну БД `dentiva_test` и роняют друг друга.
- Не запускать `sync_agent.py`, не проверив дифф — синк переписывает живого агента целиком.
- Все цифры помечать: замер или оценка. В этом проекте уже была история, когда оценки выдавались за факты и решения принимались по ним.
- Найденное у себя — говорить первым. Половина самых серьёзных багов в этом документе найдена своими же руками через час после того, как была внесена.

## 11. С чего начать ревью

1. `GET /health/detailed` — жив ли прод, включён ли RLS, есть ли алерты.
2. `app/webhooks/retell.py` — самый рискованный файл, тут вся логика живого звонка.
3. `app/services/availability.py` — откуда берутся предлагаемые времена.
4. `app/db.py` + `app/security.py` — граница изоляции клиник.
5. `dentiva-voice/agents/front_desk_v1/system_prompt.md` — что агент реально говорит.
6. Админка → System health → карточка Live agent — расходится ли прод с репозиторием.
7. `tests/test_routes/test_webhook_retell_phase2.py` и `test_transfer_number.py` — там описаны словами все баги, которые уже случались.

Комментарии в коде этого проекта объясняют **почему**, а не что. Если непонятно решение — скорее всего, причина написана рядом.
